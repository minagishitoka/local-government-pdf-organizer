# 開発経緯

## 2026-09-15: PDF結合実地テスト

自治体議会資料を大量処理するためのPDF整理システムを実地テスト。

基本方針は、原本を変更せず、資料を検査したうえで整理済みコピーを作成し、1000ページ・150MBを目安にPDFを結合すること。結合PDFの先頭には、原本と結合後ページの対応表を付ける。

機械処理と人間・AIの役割を分離した。

- Python: PDF検査、ページ数、累積ページ範囲、結合、対応表
- 人間/AI: 資料の意味判断、資料選択、結合順の判断
- 異常PDFは黙ってスキップせず、要確認・エラーとして残す
- 結合前後のページ数、しおり、遷移先を検証する

## v12: PDF→TXT→Word

Claude等へ大量資料を投入する際のPDF固有のページ・処理制約を回避する目的で、PDFを文字抽出してTXTへ変換し、そのTXTだけを入力としてWordを生成する工程を追加。

これは単なる書式変換ではなく、AI解析用資料を作るための工程である。

PyMuPDFでPDFから文字を抽出し、資料境界、結合PDFページ、原本PDFページをTXTに保持する。WordはTXTから生成し、PDFを直接読み直さない。

文字抽出できないページは `[TEXT EXTRACTION EMPTY: ...]` として明示し、情報が消えたことを隠さない。

## v13: タイトル検証強化

実地テストで、議事録の1ページ目が「目次」だけになっているケースなどを確認。

対策:

- `目次` だけをタイトルとして採用しない
- AIが元ファイル名をそのまま返した場合は要確認
- AIが怪しい場合は加工した不完全タイトルを使わず、元ファイル名へフォールバック
- `.pdf.pdf` の二重拡張子を防止

## v14: タイトル取得を冒頭3ページへ

1ページ目だけをAIへ渡す方式では、1ページ目が目次の議事録で正式タイトルを取り損ねることが判明。

そのため、タイトル判定用に冒頭最大3ページをAIへ渡す方式へ変更。

白馬村議会資料の実データで、4資料・459ページの結合、TXT化、Word化まで成功した。

## 2026-09-16: Geminiレビュー

Geminiにv14を独立レビューさせた。

総合評価は「軽微な修正後に実用投入可能」。

主な指摘:

1. API 429時、5並列の他処理が継続してAPIを呼ぶため、レート制限が連鎖する可能性
2. TXT→Wordで `【資料 001】` や `[PDF PAGE ...]` のような境界文字列が本文中に出た場合、構造を誤認する可能性
3. state.jsonに古いキーが残る可能性

追加テスト候補として、429負荷、境界文字列、1000ページ級スキャンPDF、途中ページ破損PDFなどが挙げられた。

## 2026-09-16: Claudeレビュー

Claudeにも同じv14を独立レビューさせた。

総合評価は「軽微な修正後に実用投入可能」。致命的問題はなし。

Claudeはコード上の具体的な問題を発見した。

### 発見1: 同名衝突時の `.pdf.pdf` 再発

`build_unique_filename()` の最初の候補では拡張子を除去した `clean_title` を使っているが、同名衝突時の2件目以降で元の `title` を使っていたため、元タイトルが `資料.pdf` の場合に `資料.pdf_2.pdf` が発生し得た。

v15では衝突時も `clean_title` を使うよう修正。

### 発見2: TXT→Word資料欠落の未検知

Word生成時、TXTから見つけた資料見出しを数えるだけで、元の資料台帳との完全な対応照合がなかった。

v15では資料数だけでなく、資料番号、順序、タイトルを元の `group_records` と照合し、不一致をエラーとして扱う方針に変更。

## v15: 査読反映版

v14をベースに、Claudeの具体的なバグ指摘を修正。

また、Geminiの境界文字列指摘は実験で再現可能な弱点であることを確認した。これは次の修正候補として扱い、API 429耐性と合わせて負荷・異常系テストを行う。

## 開発方針

このプロジェクトでは、AIにコードを書かせて終わりにはしない。

1. 実データで試す
2. Gemini等の別AIにレビューさせる
3. Claude等の別AIにも独立レビューさせる
4. 指摘を「実際に起きる問題」と「理論上の堅牢性問題」に分ける
5. 再現テストを行う
6. 複数の査読を比較して修正範囲を決める

「きれいなコード」よりも、研究資料を黙って欠落・改変しないことを優先する。
